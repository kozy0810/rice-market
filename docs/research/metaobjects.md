# メタオブジェクトによる派遣元マスタ

## 設計

設定 > メタフィールドとメタオブジェクト から、管理画面上でカスタムデータを定義できる。想定する構成:

- **メタオブジェクト「派遣元」** — 組織名、登録用トークン、ロイヤリティ率などを持つマスタ
- **顧客メタフィールド「所属派遣元」** — 上記メタオブジェクトへの参照

定義の作成は構築時に一度だけ行えばよく、**その後の派遣元の追加は管理画面からのノーコード操作で完結する**。要件の「管理者がダッシュボードから追加する」を満たす。なお米トレーサビリティ法で産地情報が必要になる場合も、商品メタフィールドで対応できる。

## 実証: 管理画面からの派遣元追加

要件「派遣元情報は、管理者がダッシュボードから追加する」が本当にノーコードで成立するかを確認した。アプリが所有するメタオブジェクト（`$app:dispatch_org`）がマーチャントの管理画面から編集できるかは、`access.admin = "merchant_read_write"` を設定しただけでは確証がなかったためである。

### 結果: 成立する

コンテンツ > メタオブジェクト に「派遣元組織」が表示され、一覧に組織名・登録トークン・有効が列として並ぶ。「エントリーを追加」から専用のフォームが開く。

```
派遣元組織を追加
  組織名 *          [                    ]
  登録トークン *    [                    ]
                    /a/signup/<このトークン> で登録ページが開く
  有効              ( ) True  ( ) False
  ハンドル          自動生成されたエントリーのID
```

**`shopify.app.toml` に書いたフィールドの説明文が、そのまま運用者向けのガイドとして表示される。** これは運用マニュアルの一部を定義ファイルに埋め込めることを意味する。

実際に管理画面から1件追加して保存し、API で反映を確認した。

```
agency-sakura                              | さくら協同組合     | 7f3a9c2e5b81 | active=true
app--425654222849--dispatch-org-xwj283o5   | みどり事業協同組合 | b41d7e6a9c02 | active=true
```

**非エンジニアが管理画面だけで派遣元を追加できる。** 要件を満たす。

## 注意点: ハンドルの自動生成（実際に発生することを確認済み）

API から作成したときは `agency-sakura` という指定したハンドルになったが、管理画面から作成すると `app--425654222849--dispatch-org-xwj283o5` のような自動生成値になった。

顧客タグに `org:<handle>` を使う設計では、**このハンドルがそのままタグ名になるため読みにくくなる**。管理画面から追加した「みどり事業協同組合」の登録URLを実際に通したところ、URL解決も顧客作成も成功したが、付与されたタグは次のようになった。

```
/a/signup/b41d7e6a9c02
→ 会員登録 / 派遣元: みどり事業協同組合
→ POST → 200 登録が完了しました
   付与されたタグ: member, org:app--425654222849--dispatch-org-xwj283o5
```

顧客レコードでも確認した。

```
koji.19960810+ricetest5@gmail.com | Midori Tester | ['member', 'org:app--425654222849--dispatch-org-xwj283o5']
koji.19960810+ricetest4@gmail.com | Hanako Verify | ['member', 'org:agency-sakura']
```

API で作成したものは `org:agency-sakura` と読めるが、管理画面から作成したものは `org:app--425654222849--dispatch-org-xwj283o5` になる。**同じ設計で運用方法が違うだけでタグの可読性が壊れる。** ロイヤリティ集計は注文タグを人間が目視・絞り込みする前提なので、これは実用上の問題になる。

本番では以下のいずれかを採る。

1. メタオブジェクトに `org_code` のような短い識別子フィールドを追加し、タグにはそれを使う（**推奨**。運用者がハンドルを意識しなくて済む）
2. 追加フォームでハンドルを手動設定する運用にする（運用者の規律に依存する）
3. タグをやめて顧客メタフィールドでメタオブジェクトを参照する（Validation Function からメタフィールドを読めることは確認済みだが、注文タグでの集計は別途必要）

**推奨は1。** メタオブジェクトの定義に1フィールド足すだけで、運用者はハンドルの存在を知らなくてよくなる。

**追記（2026-09-22）**: この問題はApp Proxy方式（構成A）特有だった。App Proxyのサーバーが `org:${metaobjectのhandle}` を組み立ててタグ付けしていたため、管理画面からの追加で自動生成されたハンドルがそのままタグに漏れていた。Issue #1で構成B（Shopify Forms）を採用したことで、タグはFormごとに担当者が手入力する方式になり、この経路自体がなくなった。ただし `org_code` フィールド自体は別の理由（Formのタグ文字列と派遣元マスタがズレる問題）で引き続き採用している。実装した設計は `docs/specs/dispatch-org-tagging.md` を参照。
